## 环境与操作位置

按 `web-change-quality-gate` 的关键写入路径验证。使用现有本地 48021 项目的真实 Auth、Next.js、PostgREST、数据库及 Storage，每例创建自己的随机账号、客户、三层目录、7 份文件及 1 份非空模板。关键上传与整树删除均从页面发起。固定共享账号、全局业务规则和现有业务行保持原状，未重置数据库或启用计划任务。

本机 43197 代理只转发到已核验的同一项目 Auth、Data API 和 Storage。它匹配本次随机文件路径，在真实 Storage 已删除第一份对象后，暂存回 Web 的响应。独立服务端客户端直连 48021，通过实际 LIST 和 SQL 确认对象已经消失。代理没有模拟对象消失，也没有用 SQL 删除 Storage 元数据。[官方删除说明](https://supabase.com/docs/guides/storage/management/delete-objects)

此时原文件登记为 `deleting`，原批次为 `pending`，第一项凭证未完成，根目录仍受原批次保护。随后在这个请求正在运行时实际终止 Web，或仅把本次合成账号的数据库岗位改为推广员。Auth 中的旧岗位声明仍存在，验证的是当前数据库权限，未使用真实账号。

## 发现的夹具缺陷与实际修复

旧上传凭证筛选要求所属目录仍存在；整树已删除时，读取和清理一起漏掉上传记录。批次回收动作清单还缺少目录删除。删除合成账号后，正常外键将操作者置空，最终全表摘要发现 56 条上传凭证和 24 条目录删除凭证残留。原八场景日志明确保留退出 1，没有改写为成功。

修复 tests/learning/customer-document-upload-fixture.ts：上传凭证按本次账号与随机文件名前缀确定归属，删除目录后仍可核对；批次清理补上 delete_folder。原页面测试在清理账号前直接按账号查询全部文档操作，不复用原目录筛选。只改测试夹具和断言，保留业务审计外键及生产接口。

已按八份保存清单的文件编号、路径、指纹及目录操作编号，备份并精确回收本轮 80 条记录；删除同时核对行版本与实际影响数，原有 106 条凭证摘要完全保留。恢复脚本首次因临时列使用保留名称 xmin 在删除前回滚，改名后执行通过。未按空操作者或时间范围批量删除其他记录。

原递归删除中文桌面用例在修复后实跑通过，直接断言本账号全部操作记录为零；单文件复制和多层复制各选一项原中文桌面用例，另核对两处清理出口，共三项原回归。原八个场景的业务证据与新清理回归分开保存，不声称原整轮退出 0。旧报告中的清理全零只代表原筛选结果；本批的新断言和全表摘要才覆盖本次遗漏。恢复检查另建并清理一个合成账号，真实登录及刷新确认浏览器请求直连原 48021 API。
