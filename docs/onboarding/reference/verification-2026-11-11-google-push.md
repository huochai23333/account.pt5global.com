## 修复与源码

推送声明的 `email_verified` 原先按 JavaScript 真值判断。真实验签后，字符串 `"false"` 会进入可信路径。改为严格等于布尔值 `true`。本机证书及真实官方库的原反例为 8 通过、1 失败，修复后同组 9 项通过，并增加长期回归命令 `npm run test:mail-google-push`。

入站路由原先把所有启用的发件人配置交给路由器，管理员别名也会成为负责人，而页面选择器只接受业务员，实际出现人员编号。现复用已有的在职业务员目录，再与启用的邮件配置求交。管理员发件设置保留原用途。岗位撤回和目录查询失败均有回归。相同反例加载原路由源码时 1 通过、2 失败，现行实现 3 项通过。回归接入 `npm run test:mail-intake`，该命令原 12 项加本批 3 项共 15 通过。

## 实际链路与最终凭证

前一轮记录 13 个入站及队列场景，修复路由后追加 1 个岗位场景。有效通知通过真实 Webhook，`after` 执行实际入站与通知处理。模拟来源提供已联系客户与陌生来信，业务代码执行盲索引、路由、归档、事件结算和飞书发送。已联系记录为专属夹具，未执行真实发信。

| 验证 | 独立结果 |
| --- | --- |
| 缺身份、错签名、错受众、错服务账号、布尔或字符串未验证 | Webhook 为 400，事件表均为零 |
| 通知历史位置非法 | 400，事件表仍为零 |
| 有效签名通知 | 201，独立事件达到 `completed`，客户回复 1 条、陌生来信 0 条、忽略凭证 1 条、提醒达到 `delivered`，陌生附件下载 0 |
| 相同通知重送 | 200，返回同一事件编号，业务记录及版本一致，提醒仍为 1 条 |
| 相同消息编号但历史位置不同 | 400，原事件及业务记录一致 |
| 其他邮箱的已验证通知 | 独立记录直接 `completed`，没有新业务邮件或提醒 |
| 后台入口错误凭据 | 401，恢复夹具保持原状态 |
| 过期处理锁与 Watch | 实际恢复入口先清除锁，按数据库到期时间再次调用，原事件以第 2 次尝试完成。完整队列回执为入站成功 1、失败 0、Watch 续订 1，原收件游标保留为 102 |
| 管理员发件别名 | 当前路由产生 `unassigned` 会话，提醒交给已绑定管理员；重送仍无重复，真实编号保存在独立结果文件 |
