# 本机恢复邮件与改密验收

## 范围与链路

本批复用已有 Web 3000 和本项目 Docker，仅使用 `learning-UUID@example.invalid` 专属账号与本机 Mailpit。实际入口为账号页的「修改密码」：页面请求恢复邮件，真实 Auth 经 SMTP 投递，打开邮件进入既有 `/auth/confirm`，服务端核验后进入恢复表单。填写新密码后执行真实 Auth 更新，独立 SQL 核对同一用户编号、密码是否变化及行版本，再用无 Cookie 的新浏览器上下文验证旧密码拒绝、新密码登录和刷新后的身份。

本机 SMTP、Auth、Web 和数据库执行实际代码；响应丢失、关页和退出失败由测试在浏览器边界注入。这是本地混合集成，不证明供应商邮件投递或原受限认证套件通过。密码与恢复令牌只在内存使用，附件不保存密码或密码摘要，自动 trace、视频和敏感截图关闭。

## 已复现的缺陷与处理

| 问题 | 实际观察 | 处理 |

| 四类邮件路径覆盖外部地址 | API 外部地址已为 48021，真实恢复邮件仍指向 54321 | 四类 `GOTRUE_MAILER_URLPATHS_*` 同步为本项目 48021 的验证接口 |

| 密码已改变但提示普通服务错误 | 原响应丢失用例退出 1，独立 Auth 行版本从 1289484 到 1289513 且密码已变化，页面没有未确认说明 | 改密 Hook 区分写入回执与后续退出；超时或服务端异常提示结果未确认，建议无痕窗口核对新密码 |
| 学习测试误判预期登录警告 | 首个正常路径已核对实际新密码，却把旧密码拒绝对应的结构化诊断当成未知警告 | 只接受同窗口、同阶段、400 拒绝配对且类别准确的诊断；其余警告继续失败 |
