## 本批补齐什么

此前原CLI已验证真实网关、Edge、PostgREST、数据库及60／300秒重试，但由命令主动发出下一次HTTP。本批在可重建项目 `pt5-e2e-lead-33ef8d10` 补齐实际 `pg_cron → pg_net → Edge → SDK → PostgreSQL`，外部GitHub来源使用本机模拟。没有手动调用业务请求或派发函数、修改数据库时间、缩短重试间隔或替换生产函数。共享主项目的调度始终暂停，既有Web3000继续使用原进程26524。

复制的是当前应用结构及一条公开任务定义，不复制业务行、Auth账号、邮件配置或任务密钥。专属任务令牌重新生成，外部来源地址固定为本机。挂载函数与仓库逐份核对SHA-256，数据库函数定义、所有者与权限摘要前后一致。Supabase CLI保持2.108.0；没有升级依赖或改历史迁移。

## 怎样维护与验证

先按[操作账本](../explanation/operation-run-flow.md)区分业务运行、每次尝试和传输编号，再看后端[线索函数链](../../../../PT5-dropshipping-supabase/docs/onboarding/functions.md#线索同步示例)。`cron.job`说明何时执行入口；`cron.job_run_details`说明SQL有没有运行；`private.operation_runs`及`operation_attempts`说明业务进度；最终线索、来源和导入回执才证明数据结果。

恢复重试时不改 `next_attempt_at` 冒充真实等待，不手动增加尝试后声称自动派发，也不因为HTTP502就删除已经成功的来源。暂停调度应保留原运行编号和最早重试时间。维护同一来源的幂等性时，同时比对来源和导入回执的内容与行版本。

实际调度只在专属可重建项目启用。先核对项目标签、容器／网络、固定本机来源、空业务数据和全部任务列表；只登记明确核对过的原任务。不要在共享实例启用调度或执行reset。准备、暂停、观察、恢复和限定回收见本批保留的 `output/learning-auto-dispatch-20261111/`；每次实操使用新专属目录、项目编号和日志，不能覆盖本批凭证。

本批属于后台自动入口的Critical write验证，无页面发起按钮；实际计时器和最终数据库凭证已验证。原Web手动同步页面、用户岗位矩阵及其他任务类型分别验收，不把后台验证算作原Playwright套件通过。依据官方[定时函数](https://supabase.com/docs/guides/functions/schedule-functions)、[pg_net](https://supabase.com/docs/guides/database/extensions/pg_net)及[pg_cron](https://github.com/citusdata/pg_cron)机制，核对当前安装的实际调度文本和运行状态。
