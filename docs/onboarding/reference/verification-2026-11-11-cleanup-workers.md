# 三个后台入口与资料库清理重试

本批补齐原计划中资料库清理、媒体清理、来源物流导出三个实际入口的运行证据，并修复资料库清理的一项可复现缺陷。只在新建专属Docker项目运行合成数据；主项目仅应用已验证的新迁移，业务数据、调度暂停状态和空请求队列保持。整体仍为`partial_failed`，不代表原受限全量套件或真实供应商通过。

## 真实接线与边界

实际链路为：原数据库派发函数 → pg_net → Kong → Docker Edge → 原Supabase SDK → 实际PostgREST／Storage → 原登记与运行账本。首次复制的9份入口／共享文件记录SHA-256；修复后更新实际资料库入口，Deno检查全部8个真实入口。没有替换入口的鉴权、SDK或业务处理，也没有启动第二个Web服务。

两个清理入口是内部定时任务，没有对应的用户提交按钮，本批从实际内部HTTP入口验证；既有资料库和媒体页面验收保持各自范围。没有页面、样式、语言或Next.js配置变化，因此本批不重复浏览器与Web构建。采用`web-change-quality-gate`的内部服务路径，写入仍核对独立SQL与真实Storage，不能只看HTTP状态。

物流导出运行真实来源入口和SDK，但源表为专属实例中的三张**合成字段投影**，没有复制真实来源项目、业务数据或完整来源迁移。结论只覆盖入口、鉴权、查询、拼装、分页和游标；真实来源部署与供应商另验。方法参考[Supabase函数测试](https://supabase.com/docs/guides/functions/unit-test)。CLI固定2.108.0，没有升级到具有破坏性变更的3.x。

## 实际缺陷：重试把残留漏成零项成功

通过专属实例中仅针对一个UUID的触发器，让真实删除影响0行；Storage仍按原代码实际删除。首次资料库任务HTTP200，但数据库明确为等待重试、期望2／完成1／失败1，尝试为`partial_failed`。这里没有把HTTP200记成业务成功。

原60秒重试随后产生`succeeded`、期望0／完成0，原失败文件仍有1行。根因是`document_library_claim_cleanup()`首次领取时更新`updated_at`，重试再次按超过24小时过滤，原失败目标被漏掉。红色回归实际退出1，原始日志和残留SQL凭证保留。

新迁移`20261111120138_document_cleanup_retry_targets.sql`增加内部固定清单：

- `document_private.cleanup_manifests`按运行编号保存首次目标；外键随运行清理，启用RLS，不向浏览器角色或服务角色开放直接表访问。
- `document_library_claim_cleanup_run(uuid)`锁住当前资料库运行，首次调用原领取函数，后续返回原清单。
- `document_library_finish_cleanup_target(uuid,uuid,uuid,boolean)`核对运行与清单归属。尚未完成者调用原完成函数，保留当前权限和实际影响行数；已完成者同时核对原回执、原路径、登记不存在与Storage不存在。

两个新函数只授权服务角色；原公开函数签名、初次24小时规则、60／300／900秒重试配置、目录权限均保持。没有为旧任务增加兼容或数据迁移逻辑。原红色夹具已按精确编号完成回收，再建立独立绿色夹具。

修复后首次仍正确保留部分失败，原60秒到期后派发同一运行`e2d9489b-1332-41dc-a393-7e1b8369fa07`的第2次尝试，期望2／完成2／失败0，所有目标登记和对象均不存在。新断言要求残留0，旧代码实际得到1，因此此回归能发现原缺陷。

媒体入口另外执行真实零影响故障：第一次记录`asset_delete_failed`、完成0并等待重试；原60秒后的同一运行第2次尝试完成1，登记与对象均不存在。其原实现正确，本批未改媒体代码。
