# 逐文件职责审查

[当前覆盖表](../reference/manual-review-coverage.md)列出每个模块的已审、待审和受阻数量。

填写台账后运行 `npm run learning:refresh`，覆盖表按当前模块路径及有效摘要重新生成。源码修改而摘要未更新会退回待审计数；`npm run check:learning` 拒绝过期表，但不会替你修改台账的人工状态。

`source-review.json` 是自动语法/行数扫描；`manual-review.json` 保存明确的源码判断，两者分别维护。

进度汇报始终区分「全部文件、有效已审、待审、受阻」四个数字，满足全部＝已审＋待审＋受阻；不要用“已审一千八百份”代替总量，也不要把“剩余四十份”与总量直接比较。每批保存开始时的清单键集合，单列新增/移除文件及修改后需重审的记录，结束时核对集合差异。新增源码同批审完；职责清楚的文件应记录保留理由，不为降低行数或增加审查数量而拆分。源码审查与页面、数据库、第三方验收另列，不能相互代替。

新增或移动源码后先刷新地图，再运行 `node scripts/learning/manual-review.mjs --seed`。此命令只补齐待审记录，不批准文件，也不把旧摘要更新为新摘要。

阅读源码与直接调用方后，填写职责、数据流、权限边界、保留或拆分理由、验证入口、审查者和方法。`retained` 表示已审并保留，`refactored` 表示拆分后重新审查；`pending` 与 `blocked` 都不计为完成。不能只因文件较短或测试通过就批量批准。三项以上独立职责先拆分，历史迁移保持内容不变并记录其业务与保留理由。

源码改变后必须重新核对并填写实际 SHA-256，旧摘要会使检查失败。模块归属调整同时更新台账。资料和辅助工具本身也应接受审查。

```powershell
npm run check:learning
npm run check:learning -- --require-reviewed
```

第一条检查地图和台账的结构、覆盖及已审摘要，同时显示实际完成数量。第二条是完整人工审查的验收门槛，有待审或受阻项就失败。自动扫描的 100% 覆盖不等于人工职责审查完成。

审查结果只说明代码组织与维护入口；页面和数据库业务验证仍按[验证手册](verification.md)独立完成。
