# 权限与业务凭证

## 三层检查解决不同问题

导航决定展示什么入口；页面与服务端核验当前身份和工作范围；数据库函数、RLS 与 Storage 策略决定最终允许读取或写入什么。隐藏按钮不能保护后台数据。

Auth 验证“你是谁”，当前数据库岗位、账号状态和业务授权决定“你能做什么”。不要使用用户可编辑的 metadata、显示姓名或前端缓存作为最终授权。

## 写操作的完成链路

页面点击 → 输入与当前权限检查 → 固定业务意图编号/目标版本 → 写入或后台执行 → 权威结果读回 → 页面刷新后仍一致。

| 操作 | 应核对的最终证据 |
| --- | --- |
| 领取线索 | 线索编号、当前归属、领取周期或版本 |
| 修改订单 | 订单编号、版本、费用明细与变更记录 |
| 分配结汇 | 收款编号、分配修订、有效分配与结算金额 |
| 上传文件 | 文件登记、对象路径、大小/内容摘要及可用状态 |
| 复制资料 | 批次编号、逐项结果、对象副本与目录位置 |
| 发送邮件 | 提供商消息编号、最终任务状态与归档记录 |
| 后台同步 | 操作编号、检查点、实际更新条数与最终状态 |

HTTP 成功、按钮可点或提示出现只证明中间步骤。零影响、空内容、缺少汇率或未到终态均不能显示完成。多项处理部分成功必须使用 `partial_failed`，允许用户理解已完成和待处理部分。

## 为什么需要独立查询

调用方返回自己的请求内容不能证明数据库已经改变。验收应通过另一条读取路径查询实际记录，并刷新真实页面。测试预期要来自独立准备的自有夹具，不能从被测查询结果生成预期。

重试前先确认已有结果，避免把网络中断误认为写入失败而重复提交。邮件等外部副作用尤其需要先对账。
