## 顺着一次写入阅读

1. 页面动作前，独立SQL读出已领取线索、当前周期、负责人、来源与名称；确认专属客户名称没有现有记录。登记预定客户名“线索转换回归 + 线索UUID”和本次备注。
2. 原页面辅助真实点击添加客户、填写预定值并提交。显示成功提示后，再独立查询数据库；提示本身不算成功。
3. 凭证必须属于请求的同一线索。客户ID、双方负责人、周期及周期所属线索、创建/转换/结束人都必须是非空UUID；客户和线索负责人相同，周期负责人一致，实际创建/结束人对应转换人。客户必须是未关联注册账号的销售建档客户，修订为正整数，名称非空，三个时间可解析，周期已按转换结束。
4. 完整凭证还要符合提交前清单的客户名、备注、周期与负责人，然后绑定实际客户编号、版本和修订，供后续清理核对。转换人可以是有权处理的管理员，不要求创建人必然等于客户负责人。

## 大厅怎样准备与收尾

[原大厅测试](../../../tests/e2e/sales-leads.spec.ts)每例在准备前登记随机UUID，复用后端纯SQL构造器创建一条专属线索，再由另连接确认身份、状态和影响数。上下文显式继承测试的baseURL，创建后立即登记，因此newPage失败也能关闭；关闭失败仍继续回收转换和线索，正文与各收尾错误一同保留。转换前登记的清单仍由原辅助管理，不能从任意客户编号反推可删除范围。

竞争、联系、主动退回、再次认领和转换均按同一UUID独立查实际负责人、周期、联系及行版本。管理员分配读取实际选择的业务员；查询当天额度采用上海自然日，只检查，不挪动既有claimed_at。失败竞争须完整记录不变，刷新须与独立读回一致。原页面三例仍未执行，新增390px及保留375/1440px只描述待运行的场景。

真实SQL诊断使用234版无网络副本，执行当前夹具和五组业务/故障，168张普通表的完整行与版本摘要在正常收尾后恢复；最后同ID外来样例保持原样直到整个模型销毁。浏览器、网关和传输端口明确模拟，不能当原页面或真实Auth通过。[证据与限制](../reference/verification-2026-11-09-sales-lead-history.md#2026-11-10大厅自有夹具与完整留痕)

## 管理员认领测试有什么不同

[原管理员测试](../../../tests/e2e/sales-lead-admin-claim.spec.ts)也在准备前登记UUID，使用相同的纯SQL构造器、独立读回和严格清理。旧reserveClaimQuota会移动已有领取日期并按开始时间收集其他新增记录，现已移除；只查上海当日额度，管理员自身两次领取需至少两个空位。缺额度应修复专属环境准备，不在测试里修改历史。

管理员自领→联系→退回→再次领取→转客户，完整核对实际负责人/操作者、两次周期、一条联系及保留的版本，刷新后仍一致。管理员/业务员竞争从两个原页面按钮同时发起；两请求结束后核对仅一个周期、胜者增加一次、败者不占额度，再刷新两方看板与实际退回记录。原双角色/双语言规则场景保留，375/1440px加390px；只在details尚未展开时点summary，空文字集合不能通过，截图使用testInfo.outputPath。

原三页面仍未执行。专属副本另跑当前函数与真实数据库身份：72次SQL六组，其中真实两请求等待链由pg_blocking_pids观察，再核对唯一胜者与败者额度。SQL等待和最终记录不证明原浏览器/Auth/API竞争通过。[管理员证据](../reference/verification-2026-11-09-sales-lead-history.md#2026-11-10管理员自领与真实sql竞争)

## 原转换套件的数据生命周期

[原转换测试](../../../tests/e2e/sales-lead-conversion.spec.ts)保留5个声明/6个展开场景，页面负责原双语表单、重复点击、客户编辑及故障表现；独立夹具负责数据准备、凭证和清理。它不再预删固定编号或E2E-CONVERSION来源前缀，也不一次准备8条不同日期的历史线索。实际登录返回的邮箱先独立匹配活动身份，每次仅创建当前场景需要的随机线索，核对影响数后调用真实领取规则；当天不足5条才能准备下一条，不调整旧日期。

联系方式保留六渠道和多行真实草稿；当前断言用String.raw保留正则\s，修复原重复转义。中文保留1440/375px并加390px，英文截图明确390px，所有截图按testInfo.outputPath区分；这些视口仍需原Auth页面实际验收。客户名称在页面提交前固定为“线索转换回归 + UUID”，因此转换后列表仍按线索名称查找，客户页按独立客户名查找，不能混为同一标题。

普通confirm第一次绑定完整转换凭证，之后不接受未知客户编号、时间或修订。备注编辑必须先登记旧凭证与预期新备注；独立读回只允许备注变化、修订+1和有效的新时间，其他完整字段必须相同，才能更新清理基线。负责人错误注入按实际管理员身份经过保护触发器，只更新已登记客户及精确版本；恢复前须与本次故障后的完整快照一致，期间其他修改会拒绝，不能覆盖或自动收编为夹具。

收尾先等待正在处理的拦截，再关闭页面，再按创建逆序逐条核对转换和父子删除；正文、拦截、关闭及各数据错误全部保留，错误携带本次UUID。创建已经提交但回执丢失也能按事前登记编号处理。没有转换时不擅自删除同名外来客户；归属/版本不符时保留数据，依赖专属可重建实例整体生命周期回收。[本批完整记录](../reference/verification-2026-11-09-sales-lead-history.md#2026-11-10原转换页随机夹具与编辑保护)

## 为什么清理也要单独验证

只凭线索ID先解除关联，再删除客户，可能在删除0行后留下孤立客户。现在先锁线索，再锁实际客户；核对清单的来源、名称、周期、负责人、客户种类、注册关联、创建人、备注及已绑定版本/修订。客户删除失败时，线索解除和客户删除必须一同回滚。

SQL实际重置和删除数都必须为1。提交后，另开连接按父行ID以及精确客户ID/预定名称核对：客户为零、父行保持预定身份且已无客户关联，才结束。重复清理返回删除0、重置0，也必须独立确认没有残留；它不是又删除了一次。

没有转换时，不擅自退回已有认领。没有本进程在页面前登记的清单时，不接受任意ID清理。清单在进程内保留供失败重试；整个测试进程终止后的数据由专属可重建实例生命周期回收，原调用方的全场景收尾仍需单独验收。历史领取周期不由这个转换清理器删除，其内容和行版本应保持。

## 可直接执行的专项

在Web仓库根目录运行，不需要账号、Docker或真实服务，不加载原认证入口：

```powershell
node --test scripts/learning/sales-lead-conversion-fixture.test.mjs
```

预期33项通过、0失败：原14项凭证与清理，大厅/管理员各5项生命周期，再加9项原转换夹具回归。新增部分只执行当前独立夹具或抽取的准备/资源/收尾函数，不加载原测试模块或Auth；覆盖预登记编辑、错误版本、创建丢回执、多条逆序收尾、负责人恢复竞争及真实草稿多行断言。命令/页面端口明确模拟，实际校验器、SQL构造器、目标准入和辅助接线参与；不是33次真实数据库或业务浏览器测试。完整学习工具集合使用项目声明的npm执行`npm run test:learning`。

需要执行原页面时，必须另备完整的专属API/Auth/DB实例和原入口准入；五个声明为`PLAYWRIGHT_BASE_URL`、`NEXT_PUBLIC_SUPABASE_URL`、`PT5_E2E_FIXTURE_MODE=disposable`、`PT5_E2E_DATABASE_PROJECT`及`PT5_E2E_DATABASE_CONTAINER`。程序还会实际核对项目标签、DB/Kong网络、API映射和`off/0/0`，不会因为声明了disposable就允许共享项目。此页不提供重置现有账号或全局数据的命令。

本批真实SQL诊断另用234版无网络结构副本执行实际转换函数、原子清理、零影响和两连接锁等待；API/Kong元数据接线明确模拟。结果和限制见[本批验证记录](../reference/verification-2026-11-09-sales-lead-history.md#2026-11-10转换辅助与独立凭证)，不要将这类SQL模型写成原Auth页面或默认完整API接线通过。
